**2.3. Особенности TCP**

Необходимо понимать, что TCP предоставляет упорядоченный поток байтов, а не последовательность самостоятельных сообщений приложения.

Один вызов send() не гарантирует передачу всех запрошенных байтов за один вызов.

Один вызов recv() не гарантирует получение полного сообщения приложения.

Следовательно, при разработке собственного протокола необходимо определить:

-      способ выделения границ сообщений;

-      максимальный размер сообщения;

-      порядок обработки неполных сообщений;

-      реакцию на некорректную длину;

-      правила завершения соединения.

**2.4. Особенности UDP**

Необходимо понимать, что UDP:

-      передает отдельные датаграммы;

-      не требует установления TCP-соединения;

-      не гарантирует доставку;

-      не гарантирует порядок доставки;

-      допускает потерю, повторное получение или изменение порядка получения сообщений.

Если индивидуальный вариант предусматривает подтверждение доставки или повторную передачу, соответствующая логика должна быть реализована на прикладном уровне.

-      типовые протоколы Echo, Daytime, Time и HTTP.

**3. Общая постановка задачи**

Разработать сетевое приложение или комплекс приложений для Windows в соответствии с индивидуальным вариантом.

Программа должна обеспечивать взаимодействие независимых процессов посредством TCP или UDP.

В зависимости от варианта необходимо реализовать:

-      сервер и одного или нескольких клиентов;

-      сетевую службу;

-      удаленный командный интерпретатор;

-      сетевой протокол;

-      сетевую диагностическую утилиту.

Основные сетевые операции должны выполняться посредством Windows Sockets API.

**Основной язык реализации – C или C++.**

Использование других языков допускается по согласованию с преподавателем при условии непосредственной работы с сокетами и реализации изучаемых сетевых механизмов.

Допускается использование стандартных библиотек для обработки данных, строк, JSON, математических вычислений и построения пользовательского интерфейса.

Не допускается подмена основной сетевой логики готовым сетевым фреймворком, полностью скрывающим создание сокетов, установление соединений и передачу данных.

Приложение может быть консольным. Графический интерфейс не является обязательным.

**4.3. Ограничения сетевого взаимодействия**

По умолчанию сервер должен прослушивать только локальный интерфейс 127.0.0.1.

Тестирование между двумя компьютерами в учебной сети допускается с разрешения преподавателя.

Запрещается:

-      выполнять сканирование посторонних сетей;

-      отправлять большое количество запросов сторонним серверам;

-      использовать сетевые приложения для несанкционированного доступа;

-      создавать сетевую нагрузку, способную нарушить работу учебной сети;

-      реализовывать неограниченное удаленное выполнение команд операционной системы.

Все предусмотренные заданиями диагностические эксперименты должны выполняться на собственных тестовых сервисах либо на узлах, для которых получено разрешение.

**4.4. Формат сообщений**

Для вариантов с собственным прикладным протоколом необходимо разработать и документировать формат сообщений.

Сообщение должно содержать, где применимо:

-      версию протокола;

-      тип сообщения;

-      идентификатор запроса;

-      идентификатор отправителя;

-      полезную нагрузку;

-      дополнительные поля конкретного варианта.

Для TCP рекомендуется использовать формат:

[Length: 4 bytes][Payload: Length bytes]

Поле Length – беззнаковое 32-битное число в сетевом порядке байтов.

Полезная нагрузка может передаваться в UTF-8 с использованием JSON или собственного формата.

Максимальный размер одного сообщения собственного протокола – 65536 байтов.

Для передачи более крупных данных необходимо реализовать разбиение на сообщения.

Для UDP-приложений одно сообщение должно помещаться в одну датаграмму. Рекомендуемый предел полезной нагрузки – 1200 байтов.

Для вариантов, реализующих стандартные протоколы, формат сообщений определяется соответствующей спецификацией.

**17. Индивидуальные варианты заданий**

**Раздел А. Интерактивное взаимодействие пользователей**

**Вариант 6. Децентрализованный TCP-чат**

**Протокол:** TCP.

**Архитектура:** не менее трех равноправных узлов.

Каждый узел должен одновременно:

-      принимать входящие TCP-соединения;

-      устанавливать соединения с другими узлами;

-      отправлять сообщения;

-      принимать и пересылать сообщения.

Выделенный центральный сервер отсутствует.

Сообщение содержит:

-      messageId;

-      идентификатор отправителя;

-      адресата;

-      текст;

-      TTL – максимальное количество оставшихся переходов.

Допускается передача сообщения через промежуточные узлы.

Необходимо предотвращать бесконечную пересылку с помощью TTL и учета ранее обработанных messageId.

**Эксперименты:** цепочка из 3 и 4 узлов.

**Проверить:** доставку через промежуточный узел, обработку неизвестного адресата и прекращение пересылки по TTL.
