# Протокол прикладного уровня Lab 05 Chat, версия 1

## Транспорт

Используется TCP. TCP предоставляет упорядоченный поток байтов и не сохраняет
границы сообщений приложения, поэтому границы задаются собственным
кадрированием.

## Кадрирование

Каждое сообщение передаётся одним кадром:

```text
+----------------+---------------------------+
| Length: 4 байта| Payload: Length байт      |
| network order  | UTF-8                     |
+----------------+---------------------------+
```

- `Length` — беззнаковое 32-битное целое в сетевом порядке байтов
  (`htonl`/`ntohl`).
- `1 <= Length <= 65536`.
- Нулевая или слишком большая длина считается ошибкой протокола; соединение
  закрывается.

## Полезная нагрузка

Payload — текст UTF-8, состоящий из строк `key=value`, разделённых `\n`.
Порядок полей не важен. В значениях экранируются символы `\` (`\\`), перевод
строки (`\n`) и возврат каретки (`\r`).

### Обязательные поля

| Поле | Тип | Назначение |
|---|---|---|
| `type` | строка | `HELLO`, `CHAT` или `ERROR` |
| `ver` | целое | версия протокола, сейчас `1` |
| `id` | строка | идентификатор отправителя |

### Поля сообщения CHAT

| Поле | Тип | Ограничение | Назначение |
|---|---|---|---|
| `msgid` | строка | не пустая | уникальный идентификатор сообщения |
| `dest` | строка | не пустая | идентификатор адресата |
| `ttl` | целое | 0..64 | сколько ещё переходов разрешено |
| `text` | строка | до 4000 байт | текст сообщения |
| `sent_us` | целое | >= 0 | необязательная метка времени отправки, микросекунды epoch |

`sent_us` используется только для измерения задержки доставки. Пересылающее
узел не изменяет это поле, поэтому получатель вычисляет полное время от
вызова отправки до доставки.

### Поля сообщения ERROR

| Поле | Тип | Назначение |
|---|---|---|
| `code` | строка | машинный код ошибки, например `BAD_MESSAGE` |
| `text` | строка | пояснение |

## Типы сообщений

| Тип | Отправитель | Получатель | Содержимое | Ожидаемая реакция |
|---|---|---|---|---|
| `HELLO` | любой узел | любой узел | `id` | сохранить идентификатор для соединения |
| `CHAT` | любой узел | любой узел | `msgid`, `dest`, `ttl`, `text`, `sent_us` | доставить, переслать или отбросить |
| `ERROR` | любой узел | любой узел | `code`, `text` | записать в журнал |

## Правила обработки CHAT

1. Проверить наличие и корректность полей.
2. Если `msgid` уже встречался, увеличить `dropped_dup` и не обрабатывать
   сообщение повторно.
3. Если `dest == id` текущего узла — доставить сообщение локальному
   пользователю, увеличить `delivered`.
4. Если `dest != id` и `ttl > 0` — уменьшить TTL на 1 и переслать сообщение
   всем активным соединениям, кроме соединения, из которого оно пришло.
   Увеличить `forwarded`.
5. Если `dest != id`, `ttl == 0` — отбросить сообщение и увеличить
   `dropped_ttl`.
6. Если пересылать некуда (нет других активных соединений) — увеличить
   `dropped_no_route`.

Узел-отправитель также запоминает `msgid` своего сообщения, чтобы не принять
его обратно и не начать повторную пересылку.

## Пример

Сообщение от узла A узлу C через узел B:

```text
type=CHAT
ver=1
id=A
msgid=A-1794235576839-0
dest=C
ttl=5
text=payload #1
sent_us=1794235576839123
```

После пересылки узлом B:

```text
type=CHAT
ver=1
id=A
msgid=A-1794235576839-0
dest=C
ttl=4
text=payload #1
sent_us=1794235576839123
```

## Коды ошибок

| Код | Причина |
|---|---|
| `BAD_MESSAGE` | отсутствует обязательное поле, неверный TTL, неизвестный тип, слишком длинный текст |
| `INVALID_FRAME` | неверная длина кадра (обрабатывается закрытием соединения) |

## Ограничения

- Максимальная полезная нагрузка: 65536 байт.
- Максимальный текст: 4000 байт.
- TTL: 0..64.
- Версия протокола: 1.
- Неизвестные дополнительные поля игнорируются для совместимости.
- Неизвестный тип сообщения является ошибкой протокола.
