# Архитектура лабораторной работы № 4

## 1. Общая идея

Модель «Обедающие философы» реализуется потоками одного процесса. Каждый
философ имеет уникальный номер и TID. Вилки являются разделяемыми ресурсами.
Доступ к ним предоставляется только через центральную очередь заявок.

Заявка философа содержит сразу обе соседние вилки. Поэтому философ либо
получает обе вилки, либо не получает ни одной. Это исключает удержание одного
ресурса в ожидании второго и, следовательно, исключает классическую
взаимоблокировку.

## 2. Участники и общие ресурсы

### Потоки

- `N` потоков-философов;
- главный поток: разбор параметров, запуск, ожидание завершения, сводка;
- watchdog главного потока: контроль максимальной длительности эксперимента.

### Общие ресурсы

- `fork_owner[N]` — номер философа, владеющего вилкой, или `-1`;
- очередь заявок `std::deque<Request*>`;
- состояния философов;
- счётчики статистики;
- журнал событий (защищён отдельным мьютексом).

Все перечисленные общие данные, кроме журнала, защищены одним мьютексом
`cs`, который играет роль `CRITICAL_SECTION`.

## 3. Основные структуры

```cpp
enum class PhilosopherState {
    THINKING,
    WAITING,
    EATING,
    FINISHED
};

enum class RequestStatus {
    WAITING,
    GRANTED,
    CANCELLED
};

struct Request {
    int philosopherId;
    int leftFork;
    int rightFork;
    RequestStatus status;
    std::chrono::steady_clock::time_point enqueuedAt;
    std::chrono::steady_clock::time_point grantedAt;
    sem_t event;                 // аналог auto-reset Event
};

struct PhilosopherStats {
    int completedCycles = 0;
    int timeouts = 0;
    int overtakes = 0;
    double totalWaitMs = 0.0;
    double maxWaitMs = 0.0;
};

struct SharedState {
    std::mutex cs;               // аналог Critical Section
    std::deque<Request*> queue;
    std::vector<int> forkOwner;
    std::vector<PhilosopherState> states;
    std::vector<PhilosopherStats> stats;
    std::atomic<bool> stop{false};
};
```

Объект `Request` создаётся философом на время одной попытки получения вилок.
Его event инициализируется перед постановкой в очередь и уничтожается после
завершения попытки.

## 4. Жизненный цикл заявки

1. Философ заканчивает обдумывание.
2. Под `cs` создаёт заявку, переводит себя в `WAITING`, кладёт заявку в конец
   очереди и вызывает `dispatch_locked()`.
3. Если заявка может быть удовлетворена, `dispatch_locked()` назначает
   владельцев вилок, переводит заявку в `GRANTED`, удаляет её из очереди и
   выполняет `sem_post()`.
4. Философ ожидает на своём event с тайм-аутом. Если event уже был отправлен
   до начала ожидания, семафор сохраняет разрешение, поэтому сигнал не
   теряется.
5. После пробуждения философ под `cs` проверяет статус заявки:
   - `GRANTED` — переходит к еде;
   - `WAITING` и тайм-аут истёк — удаляет заявку из очереди, переводит её в
     `CANCELLED`, увеличивает счётчик тайм-аутов.
6. После еды философ под `cs` освобождает обе вилки, увеличивает счётчик
   выполненных циклов и вызывает `dispatch_locked()`, чтобы передать вилки
   следующим ожидающим.
7. После выполнения всех циклов философ переходит в `FINISHED`.

Проверка статуса и удаление заявки выполняются под тем же `cs`, что и выдача.
Поэтому ситуация «заявку выдали одновременно с отменой» разрешается
однозначно: философ видит либо `GRANTED`, либо `WAITING`.

## 5. Алгоритм выдачи вилок

Функция `dispatch_locked()` вызывается только при удерживаемом `cs`.

### Режим FIFO

```text
while queue not empty:
    request = queue.front()
    if forkOwner[left] == -1 and forkOwner[right] == -1:
        grant(request)
        queue.pop_front()
    else:
        break
```

Свойства:

- заявка не может обойти голову очереди;
- если голову невозможно удовлетворить, более поздние заявки ждут;
- счётчик `overtakes` должен оставаться равным нулю.

### Режим SCAN

```text
for request in queue from front to back:
    if forkOwner[left] == -1 and forkOwner[right] == -1:
        if request is not at the front:
            stats[request.id].overtakes++
        grant(request)
        remove request from queue
```

Свойства:

- заблокированная заявка может быть обойдена;
- возможны голодание и большой разброс времени ожидания;
- количество обходов фиксируется для анализа несправедливости.

## 6. Синхронизация

### Критическая секция

Один `std::mutex` защищает:

- очередь заявок;
- владельцев вилок;
- состояния философов;
- счётчики статистики;
- проверку и изменение статусов заявок.

Это гарантирует, что проверка «обе вилки свободны» и назначение владельцев
выполняются как единая атомарная операция.

### Event на заявку

Для каждой заявки используется `sem_t` с начальным значением 0:

- `sem_post()` соответствует `SetEvent()`;
- `sem_timedwait()` соответствует `WaitForSingleObject()` с тайм-аутом.

Auto-reset-семантика обеспечивается тем, что каждой заявке соответствует
отдельный семафор и ровно одна выдача. Сигнал, отправленный до вызова
`sem_timedwait()`, не теряется: семафор сохраняет значение 1.

### Ожидание и тайм-аут

Ожидание выполняется с абсолютным дедлайном. При истечении тайм-аута философ
под `cs` проверяет, не была ли заявка уже выдана. Если нет — заявка
отменяется и удаляется из очереди. После отмены вызывается
`dispatch_locked()`, так как следующая заявка могла стать доступной.

### Завершение

После выполнения всех циклов потоки философов завершаются. Главный поток
выполняет `join()`, затем проверяет финальные инварианты:

- очередь пуста;
- все вилки свободны;
- все философы в состоянии `FINISHED`;
- каждый философ выполнил заданное число циклов;
- число нарушений инвариантов равно нулю.

При превышении `--max-duration-ms` устанавливается флаг остановки, ожидающие
потоки пробуждаются, эксперимент завершается с диагностикой. Такой запуск не
считается корректным экспериментальным результатом.

## 7. Состояния философа

```text
[*] -> THINKING
THINKING -> WAITING     после обдумывания, при постановке заявки
WAITING -> EATING       если заявка выдана
WAITING -> THINKING     при тайм-ауте и отмене заявки
EATING -> THINKING      после еды и освобождения вилок
THINKING -> FINISHED    после выполнения всех циклов
```

Состояние `WAITING` означает, что заявка находится в очереди. Состояние
`EATING` означает, что обе вилки уже закреплены за философом.

## 8. Журнал и статистика

Журнал событий защищён отдельным мьютексом. Формат записи:

```text
[000125 ms] P2 WAITING RESOURCE=2,3
[000131 ms] P2 ACQUIRED RESOURCE=2,3
[000145 ms] P2 EATING
[000153 ms] P2 RELEASED RESOURCE=2,3
```

Для измерения производительности подробный журнал отключается. Итоговая
сводка содержит:

- общее время;
- пропускную способность;
- число выполненных циклов;
- число тайм-аутов;
- среднее и максимальное время ожидания;
- распределение ожидания по философам;
- количество обходов (`overtakes`);
- максимальную длину очереди;
- количество нарушений инвариантов.

## 9. Проверяемые инварианты

1. `forkOwner[i]` не может одновременно обозначать двух владельцев.
2. Если философ находится в `EATING`, обе его вилки принадлежат ему.
3. Число занятых вилок равно `2 * число философов в EATING`.
4. Длина очереди не превышает `N`.
5. У одного философа не может быть более одной активной заявки.
6. В режиме FIFO отсутствуют обходы.
7. В конце работы нет занятых вилок и активных заявок.
8. Каждый философ выполнил ровно `--cycles` циклов.

Нарушения увеличивают общий счётчик и выводятся в сводке. Для корректной
конфигурации ожидается `INVARIANT_VIOLATIONS=0`.

## 10. Обработка ошибок

Проверяются:

- корректность аргументов командной строки;
- результаты создания потоков;
- инициализация и уничтожение семафоров;
- ошибки открытия журнала и CSV;
- тайм-ауты ожидания;
- превышение максимальной длительности;
- невозможность корректно завершить поток.

При ошибке программа освобождает захваченные ресурсы, закрывает дескрипторы и
возвращает ненулевой код завершения.

## 11. Принятые проектные решения

- **Потоки, а не процессы.** Модель требует общих ресурсов; потоки проще и
  допускаются заданием.
- **Один мьютекс на состояние.** Упрощает доказательство корректности и
  исключает гонки между проверкой и изменением владельцев вилок.
- **Event на каждую заявку.** Позволяет точечно будить нужного философа и
  естественно реализует тайм-аут.
- **Нет отдельного потока-арбитра.** Очередь централизована, а выдача
  выполняется тем потоком, который меняет состояние под критической секцией.
  Это уменьшает сложность завершения и не влияет на корректность.
- **Атомарный захват двух вилок.** Исключает взаимоблокировку без
  дополнительных иерархий ресурсов.
- **FIFO и SCAN в одном коде.** Различие сосредоточено в
  `dispatch_locked()`, что упрощает сравнение режимов.
