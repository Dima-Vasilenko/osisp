**Некоторые служебные и технологические задачи**

**1. Цель работы**

Изучить системные механизмы операционной системы Windows, используемые для
конфигурирования, мониторинга, журналирования, обработки оконных сообщений и
построения многомодульных приложений.

В ходе выполнения лабораторной работы необходимо:

- изучить назначение и структуру реестра Windows;
- освоить программные интерфейсы для чтения, поиска, изменения и контроля
  данных реестра;
- получить навыки сбора и анализа системной информации;
- изучить механизмы журналирования событий Windows;
- освоить средства перехвата и протоколирования оконных сообщений;
- изучить принципы построения динамически подключаемых библиотек DLL;
- освоить способы загрузки и использования внешних программных модулей;
- приобрести навыки разработки служебных и диагностических утилит;
- научиться обрабатывать системные ошибки и корректно освобождать ресурсы;
- закрепить навыки использования Git для сопровождения разработки.

**2. Теоретическая и методическая часть**

Перед выполнением лабораторной работы необходимо изучить следующие вопросы.

**2.1. Конфигурирование Windows**

- Назначение реестра Windows.
- Иерархическая структура реестра.
- Разделы и значения реестра.
- Основные корневые разделы.
- Типы данных REG_SZ, REG_EXPAND_SZ, REG_DWORD, REG_QWORD, REG_MULTI_SZ,
  REG_BINARY.
- Права доступа к разделам.
- Создание, открытие, перечисление и удаление разделов и значений.
- Экспорт и восстановление данных реестра.
- Обнаружение изменений.

Основные функции Windows API: RegOpenKeyEx(), RegCreateKeyEx(),
RegQueryValueEx(), RegSetValueEx(), RegEnumKeyEx(), RegEnumValue(),
RegDeleteValue(), RegDeleteKeyEx(), RegDeleteTree(), RegNotifyChangeKeyValue(),
RegCloseKey().

**2.2. Получение системной информации**

Изучить основные характеристики процессора, конфигурацию оперативной памяти,
сведения о логических дисках, параметры операционной системы, сведения о
процессах, системное время и время работы системы, системные функции получения
аппаратной информации, основы WMI. Примеры функций: GetNativeSystemInfo(),
GlobalMemoryStatusEx(), GetLogicalDriveStrings(), GetDiskFreeSpaceEx(),
GetVolumeInformation(), GetSystemTimes(), GetTickCount64(),
GetComputerNameEx(). Допускается использование WMI и дополнительных Windows
API, если это предусмотрено вариантом.

**2.3. Журналирование событий**

Изучить назначение журналирования, структуру события, источник события,
идентификатор события, уровни важности, журналы Application и System,
фильтрацию событий, экспорт событий, регистрацию источников событий. Основные
функции Windows Event Log API: EvtQuery(), EvtNext(), EvtRender(), EvtClose(),
EvtSubscribe(). Для вариантов с записью собственных событий могут применяться
RegisterEventSource(), ReportEvent(), DeregisterEventSource(). Необходимо
различать чтение существующих журналов и регистрацию нового источника событий,
которая может потребовать предварительной настройки системы с повышенными
правами.

**2.4. Перехват оконных сообщений**

Изучить понятие оконного сообщения Windows, очередь сообщений, обработчик
оконных сообщений, GetMessage(), DispatchMessage(), SendMessage(),
PostMessage(), механизм Windows Hooks, область действия перехватчика,
подключение и удаление обработчика. Основные функции: SetWindowsHookEx(),
CallNextHookEx(), UnhookWindowsHookEx().

**2.5. Динамические библиотеки и многомодульные приложения**

Изучить назначение программных библиотек, статические и динамические
библиотеки, структуру DLL, таблицу экспортируемых функций, загрузку DLL, явное
и неявное связывание, поиск экспортируемых функций, освобождение модулей,
соглашения о вызове, совместимость интерфейсов, смешанные сборки Windows.
Основные функции: LoadLibrary(), LoadLibraryEx(), GetProcAddress(),
FreeLibrary(), GetModuleHandle(), GetModuleFileName().

**3. Общая постановка задачи**

Разработать приложение или программный комплекс для Windows в соответствии с
индивидуальным вариантом. Приложение должно демонстрировать непосредственную
работу с указанными механизмами операционной системы. В зависимости от
варианта необходимо реализовать утилиту работы с реестром, приложение
мониторинга изменений, средство анализа и очистки учебных данных реестра,
приложение сбора системной информации, средство анализа или записи событий,
приложение перехвата оконных сообщений, многомодульное приложение с DLL.
Основная функциональность должна использовать соответствующие системные
интерфейсы Windows API. Основной язык программирования — C или C++. Для
варианта со смешанной сборкой допускается и предусматривается использование
C++/CLI. Использование Python, MATLAB, R и других языков допускается для
обработки экспериментальных результатов, построения графиков и дополнительных
проверок. Использование готовых библиотек не должно полностью заменять
изучаемый механизм Windows API. Программа может быть консольной или оконной.
Если для выполнения варианта необходима обработка оконных сообщений, оконная
часть является обязательной.

**4. Общие требования к реализации**

**4.1. Параметры программы**

Основные параметры должны задаваться без изменения исходного кода. В
зависимости от варианта необходимо предусмотреть путь к разделу реестра,
образец поиска, максимальную глубину обхода, количество объектов, интервал
наблюдения, количество измерений, формат экспорта, режим работы, выбранную
библиотеку, количество операций, параметры фильтрации. Допускается
использование аргументов командной строки, консольного меню, конфигурационного
файла или графического интерфейса.

**4.2. Ограничение области работы с реестром**

Для операций изменения и удаления данных разрешается использовать исключительно
специально созданную учебную область:

HKEY_CURRENT_USER\Software\OSiSP\Lab06\Student_<STUDENT_ID>\Run_<RUN_ID>

Студент самостоятельно создает необходимые подразделы и значения. Изменение
или удаление данных за пределами учебной области запрещается. Поиск и просмотр
системных разделов допускаются только в режиме чтения и в пределах прав
текущего пользователя. Не допускается изменение системных параметров Windows,
параметров безопасности, автозагрузки и конфигурации установленных приложений.

**4.3. Ограничения на использование WinHook**

Перехват оконных сообщений допускается только для окон и потоков собственного
учебного приложения. Не допускается установка глобальных перехватчиков для
всех приложений, запись текста, вводимого пользователем в посторонних
программах, перехват сообщений чужих процессов, скрытая регистрация действий
пользователя, использование механизмов внедрения DLL в сторонние процессы.

**4.4. Проверка системных вызовов**

Каждый существенный вызов Windows API должен сопровождаться проверкой
результата. При ошибке необходимо отображать название функции, код ошибки,
текстовое описание, выполнявшуюся операцию. Для функций реестра, возвращающих
код состояния непосредственно, необходимо использовать возвращенный код, а не
автоматически обращаться к GetLastError().

**4.5. Освобождение ресурсов**

После завершения приложения необходимо освобождать открытые разделы реестра,
системные дескрипторы, установленные оконные перехватчики, подключенные
динамические библиотеки, объекты ожидания, выделенную память, другие ресурсы,
созданные программой.

**4.6. Журналирование**

Программа должна вести журнал основных действий. Для каждого события указывать
время, тип операции, объект, результат, код ошибки при наличии. Пример:

[10:15:01.125] REG_OPEN status=OK
[10:15:01.131] REG_ENUM key=Settings count=12
[10:15:01.142] REG_EXPORT file=backup.json
[10:15:01.150] REG_CLOSE status=OK

Для вариантов, в которых журналирование является основной задачей, действуют
дополнительные требования индивидуального задания.

**5. Индивидуализация задания**

Каждому студенту назначается STUDENT_ID от 1 до 32. Использовать:
STUDENT_ID = последние 3 цифры студенческого билета; SEED = 1000 + STUDENT_ID
* 97; RUN_ID = идентификатор запуска. Для вариантов с тестовыми данными SEED
использовать при формировании входного набора. Для вариантов с реестром
STUDENT_ID и RUN_ID использовать в имени учебного раздела. Для вариантов DLL
использовать индивидуальное название проекта и библиотеки. Студент должен
выполнить эксперименты со стандартными параметрами варианта, эксперименты со
своим индивидуальным набором данных, дополнительный эксперимент с параметрами,
назначенными преподавателем на защите.

**6. Экспериментальная часть**

**6.1. Общие требования**

Каждую исследуемую конфигурацию необходимо выполнить не менее трех раз. При
наличии случайных данных использовать фиксированный SEED. Для измерения
времени рекомендуется использовать QueryPerformanceCounter(). Все измерения
должны выполняться на одной конфигурации компьютера, если иное не предусмотрено
заданием.

**6.2. Показатели**

В зависимости от варианта определять время выполнения операции, количество
обработанных объектов, количество обнаруженных изменений, количество ошибок,
число найденных записей, длительность экспорта, время получения системной
информации, количество обработанных событий, время загрузки DLL, время
выполнения вызовов функций.

**6.3. Таблица результатов**

Конфигурация | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Среднее, мс

Дополнительно необходимо привести таблицу профильных показателей своего
варианта.

**6.4. Графики**

Необходимо построить не менее двух графиков на основании собственных
экспериментальных данных. Первый график: зависимость времени выполнения
операции от исследуемого параметра. Второй график: другая характеристика,
соответствующая варианту: количество найденных объектов, количество событий,
распределение типов данных, объем экспортированной информации, изменение
использования ресурсов, частота оконных сообщений, количество ошибок,
распределение времени выполнения. Графики должны иметь название, подписи осей
и единицы измерения.

**6.5. Анализ**

Студент должен объяснить, какие параметры изменялись, что измерялось, какие
результаты ожидались, какие результаты получены, какие ограничения
исследуемого механизма выявлены, как результаты связаны с работой операционной
системы.

**7. Требования к использованию Git**

**7.1. Общие положения**

Использование системы контроля версий Git является обязательным. Каждый
студент должен выполнять лабораторную работу в индивидуальном закрытом
репозитории. Преподавателю должен быть предоставлен доступ к репозиторию с
начала выполнения работы.

**7.2. Структура репозитория**

ossp-labs/
├── lab06-system/
│   ├── src/
│   ├── tests/
│   ├── data/
│   ├── scripts/
│   ├── diagrams/
│   ├── report/
│   └── README.md
└── .gitignore

В README.md необходимо указать номер варианта, назначение программы,
используемые Windows API, требования к среде разработки, порядок сборки,
параметры запуска, порядок воспроизведения экспериментов, ограничения доступа
и безопасности. Не допускается размещать в репозитории личные секреты, учетные
данные, конфиденциальную системную информацию или дампы реестра, содержащие
сведения, не относящиеся к лабораторной работе.

**7.3. Контрольные этапы**

Этап 1. Проектирование. Создание структуры проекта, выбор системных API,
описание архитектуры и подготовка схемы. Этап 2. Основная реализация.
Реализация основных функций приложения и первоначальная проверка. Этап 3.
Обработка ошибок и тестирование. Реализация проверок, дополнительных режимов,
обработки ошибок и тестовых сценариев. Этап 4. Эксперименты и отчет.
Проведение измерений, создание графиков, диаграмм, подготовка отчета. Для
каждого этапа необходимо создать содержательный коммит и отправить его в
удаленный репозиторий. Преподаватель вправе фиксировать хеши коммитов
контрольных версий.

**7.4. Требования к истории**

Коммиты должны отражать фактическое развитие проекта. Примеры: «Создан каркас
приложения», «Добавлен рекурсивный обход разделов реестра», «Реализован
экспорт в JSON», «Исправлена обработка REG_MULTI_SZ», «Добавлено
журналирование ошибок», «Реализованы тестовые сценарии», «Добавлен скрипт
построения графиков», «Подготовлен отчет». Не допускается искусственное
создание истории коммитов исключительно для имитации самостоятельной
разработки. Запрещается без согласования с преподавателем изменять или
удалять опубликованные контрольные версии. Количество коммитов само по себе
не является доказательством самостоятельности выполнения.

**7.5. Проверка Git**

На защите студент должен уметь показать историю коммитов, объяснить
назначение выбранного изменения, продемонстрировать отличия двух версий
проекта, показать исправление ошибки, внести небольшое изменение в программу,
создать новый коммит и отправить его в репозиторий.

**9. Требования к отчету**

Отчет должен содержать титульный лист, введение, цель работы, номер и
формулировку индивидуального задания, краткие теоретические сведения,
архитектуру разработанного приложения, описание алгоритма, перечень
использованных Windows API, описание структур данных, схемы и диаграммы,
описание обработки ошибок, описание тестовых сценариев, методики проведения
экспериментов, экспериментальные результаты, графики и анализ результатов,
заключение, список использованных источников, приложение А «Использование
искусственного интеллекта», приложение Б «Сведения о репозитории Git»,
приложение В «Листинг кода программы», приложение Г «Листинг кода графических
материалов».

В основном тексте отчета необходимо привести основные фрагменты исходного
кода, демонстрирующие работу с изучаемыми механизмами Windows. Полный исходный
код размещается в Git-репозитории.

**9. Приложения: исходные материалы графиков, схем и диаграмм**

В конце отчета необходимо привести исходные материалы, использованные для
создания графиков, схем, диаграмм и иных визуальных материалов. Предоставлению
подлежат Python-скрипты, MATLAB-скрипты, R-скрипты, исходные описания PlantUML,
исходные описания Mermaid, исходные файлы Graphviz, редактируемые файлы
draw.io, экспериментальные данные, дополнительные конфигурации, необходимые
для воспроизведения результатов.

**9.1. Текстовые исходники**

Текстовые исходники необходимо приводить в приложениях с сохранением
форматирования. Кроме того, каждый исходный файл должен находиться в
репозитории Git.

**9.2. Исходные файлы графических редакторов**

Для материалов, созданных в draw.io, Visio и других графических редакторах,
необходимо указать название редактора, имя исходного файла, путь к файлу в
репозитории. Полный XML-файл draw.io необязательно включать в текст отчета,
если он предоставлен в редактируемом виде.

**9.3. Воспроизводимость**

Преподаватель должен иметь возможность: запустить скрипт построения графика;
получить результат по предоставленным данным; открыть исходную диаграмму;
изменить ее элементы; проверить соответствие материалов основной части отчета.
Предоставление только изображений или скриншотов не заменяет редактируемые
исходники.

**9.4. Рекомендуемые приложения**

Приложение А. Исходный код Python для построения графиков. Приложение Б.
Исходное описание диаграммы PlantUML. Приложение В. Исходные файлы draw.io.

В отчете должен присутствовать отдельный раздел «Использование искусственного

**11.6. Проверка**

При защите преподаватель вправе попросить показать относящуюся к лабораторной
работе историю запросов, выбрать использованный промпт для объяснения,
попросить воспроизвести результат, выбрать фрагмент кода, созданный или
измененный с помощью ИИ, предложить изменить соответствующий фрагмент,
попросить объяснить самостоятельную проверку. При демонстрации истории
запросов допускается скрытие личной информации, не относящейся к выполнению
лабораторной работы. Само по себе применение ИИ не является основанием для
снижения оценки. Недостоверное декларирование и использование ИИ для
подготовки самого раздела рассматриваются как нарушения требований к отчету.

**11. Порядок представления работы**

Перед защитой студент обязан предоставить отчет в формате PDF, ссылку на
индивидуальный Git-репозиторий, хеш коммита окончательной версии, полный
исходный код программы, инструкцию по сборке и запуску, исходные
экспериментальные данные, исходные скрипты построения графиков, редактируемые
файлы схем и диаграмм, описание использованных Windows API.

**12. Порядок защиты**

Этап 1. Демонстрация программы. Студент запускает приложение и показывает
основную функциональность, работу используемых Windows API, обработку входных
параметров, результаты выполнения, журнал событий, корректное завершение.
Этап 2. Проверка обработки ошибок. Преподаватель выбирает один или несколько
сценариев: отсутствующий раздел реестра, недостаточные права доступа,
некорректный тип данных, отсутствие файла, недоступность журнала, неудачная
загрузка DLL, отсутствие экспортируемой функции, некорректный параметр
запуска, завершение наблюдения за объектом. Студент должен продемонстрировать
реакцию программы и объяснить соответствующий участок кода. Этап 3. Проверка
Git. Преподаватель выбирает один или два коммита. Студент должен объяснить
назначение изменений, показать соответствующий код, обосновать принятое
решение, выполнить небольшое дополнительное изменение, создать новый коммит.

**16. Итоговые требования**

Лабораторная работа считается завершенной после выполнения индивидуального
задания, корректной реализации требуемых системных механизмов, проверки
обработки ошибок, проведения экспериментов, подготовки отчета, предоставления
исходного кода, скриптов и диаграмм, представления истории разработки в Git,
успешной практической защиты. Студент должен продемонстрировать понимание
принципов работы изучаемых системных механизмов Windows, способность
самостоятельно проверять результаты и вносить изменения в созданное
программное обеспечение.

**Вариант 6. Мониторинг изменений значений**

**Основной API:** RegNotifyChangeKeyValue().

Разработать утилиту ожидания изменения значений внутри выбранного учебного
раздела.

Программа должна:

1. Открыть раздел с правом уведомления.
2. Зарегистрировать асинхронное ожидание.
3. Ожидать событие.
4. После получения уведомления повторно прочитать значения.
5. Определить разницу с предыдущим состоянием.
6. Продолжить наблюдение.

**Эксперименты:** изменение одного значения, нескольких значений и удаление
значения.

**Проверить:** получение уведомлений и корректное определение итоговых
отличий.
